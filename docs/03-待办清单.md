### 选型变更：为什么没用 SkiaSharp

P1-3 原计划「可选 SkiaSharp 处理层」。本轮改为**纯 BCL 实现**，理由：

1. 项目最大的差异化是「零原生 DLL + NativeAOT + WASM 可跑」，上一轮刚验证 AOT 23 MB 原生 exe 可用；引入 SkiaSharp 会带回 `libSkiaSharp.dll` 等平台原生库，直接抵消这个卖点。
2. 所需算子（双线性缩放、色调、几何水印）都是纯数组运算，用 BCL 完全够；字形栅格化才真正需要字体引擎。
3. 隔离成独立项目 `SimdCodecs.Processing`，Core 不引用它，桌面 / API 可选引用 —— 原计划「不污染 Core」的约束仍然满足。
4. 代价如实登记：**水印是几何图案（FNV 哈希决定斜纹相位），不渲染文字字形**；矢量绘图、透视变换也未做。若将来确需 TrueType 字体水印，可再加一个真正可选的 Skia 适配项目，不影响现有链路。

AOT 侧证据：`ImageProcessor` / `CvInput` 全部在 `aot-probe` 原生 exe 中通过 54 项自检与 6 项 GUI 冒烟，IL2026 / IL3050 警告计数为 0。
